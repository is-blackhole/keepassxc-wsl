# План реализации: `kpx`, CLI для KeePassXC через browser integration (WSL → Windows)

## Цель
Получать в WSL пароли, логины и атрибуты записей KeePassXC, который запущен на Windows. На стороне WSL ничего вводить не нужно: работает browser-integration протокол через `keepassxc-proxy.exe`.

## Стек и структура
- Node (через `source ~/.nvm/nvm.sh`), TypeScript, pnpm (версия закреплена в `packageManager`), ESM.
- Зависимости: `tweetnacl` (NaCl box, XSalsa20-Poly1305 и X25519; встроенный crypto в Node их не поддерживает). Разбор аргументов: `node:util` `parseArgs`, без лишних пакетов.
- Dev: `typescript`, `vitest`, `eslint`. Сборка через `tsc` в `dist/`, в `package.json` поле `bin: { kpx: dist/cli.js }`, установка через `pnpm link --global`.
- Папку укажет пользователь.

```
src/
  cli.ts          — команды и аргументы, коды выхода
  transport.ts    — запуск proxy, фрейминг native messaging
  protocol.ts     — шифрование, nonce, запросы и ответы, ожидание unlock
  client.ts       — высокоуровневые функции: connect(), getLogins(url)
  store.ts        — хранение ассоциаций
  select.ts       — выбор записи по фильтрам и извлечение поля
  output.ts       — форматы env/shell/json, экранирование
  template.ts     — разбор и рендер шаблонов
test/             — vitest
```

## 1. Транспорт (`transport.ts`)
- Через `spawn` запускается `KPX_PROXY`, по умолчанию `/mnt/c/Program Files/KeePassXC/keepassxc-proxy.exe`, с `stdio: pipe`.
- Запись: `uint32 LE длина` + UTF-8 JSON. Чтение: буферизованный парсер фреймов. Ответ может прийти частями или несколько фреймов сразу.
- Каждое входящее сообщение отдаётся как событие. Ошибки proxy, его завершение и таймаут (`KPX_TIMEOUT`, по умолчанию 30 с) дают понятную ошибку.
- При завершении работы proxy закрывается.

## 2. Протокол (`protocol.ts`)
- `clientID`: 24 случайных байта в base64, новый на каждую сессию.
- Эфемерная пара ключей: `nacl.box.keyPair()` на каждую сессию.
- **`change-public-keys`** (без шифрования):
  - запрос `{action, publicKey, nonce, clientID}`;
  - из ответа сохраняется `publicKey` сервера.
- **Зашифрованные запросы.** Внешний конверт: `{action, message: b64(box(JSON, nonce, serverPub, clientSec)), nonce, clientID, triggerUnlock?}`. Ответ расшифровывается через `nacl.box.open`.
- **Проверка nonce.** Nonce ответа должен быть равен nonce запроса +1 (инкремент little-endian, как `sodium_increment`). Если не совпадает, это ошибка.
- **Ошибки.** Ответ вида `{error, errorCode}` превращается в типизированную ошибку. Важные коды: 1 (база не открыта), 15 (записи не найдены), 7/8 (ассоциация).
- **Нежелательные сообщения.** `database-locked` и `database-unlocked` могут прийти в любой момент. Ответы нужно сопоставлять по `action`, а не по порядку.
- **Действия:**
  - `get-databasehash`, внутренний JSON `{action}`; вернётся `hash`.
  - `associate`, внутренний JSON `{action, key: clientPub, idKey: idPub}`; вернётся `id`.
  - `test-associate`, внутренний JSON `{action, id, key: idKey}`.
  - `get-logins`, внутренний JSON `{action, url, keys: [{id, key: idKey}]}`; вернётся `entries[]`: `name`, `login`, `password`, `uuid`, `group`, `expired`, `stringFields`, `totp?`.
  - `get-totp`, внутренний JSON `{action, uuid}`. Это опционально, для поля `totp`.
- **Разблокировка.** Если `get-databasehash` вернул код 1, отправить его повторно с `triggerUnlock: "true"`. Затем ждать `database-unlocked` (таймаут `KPX_UNLOCK_TIMEOUT`, по умолчанию 120 с) и повторить запрос.

## 3. Ассоциации (`store.ts`)
- Файл: `~/.config/kpx/assoc.json` (можно переопределить через `KPX_CONFIG`). Права: 600, папка 700.
- Формат: `{ [dbHash]: { id, idKey } }`, отдельная ассоциация на каждую базу.
- Порядок подключения:
  1. обмен ключами;
  2. получить хеш базы;
  3. если ассоциация есть, выполнить `test-associate`;
  4. если её нет или проверка не прошла, выполнить `associate` (с сообщением в stderr «подтвердите подключение в KeePassXC») и сохранить результат.
- Отдельная команда `kpx associate` запускает ассоциацию принудительно.
- `idKey` — публичный ключ постоянной пары, которая создаётся при первой ассоциации. Хранить нужно только публичную часть и `id`.

## 4. Выбор записи и поля (`select.ts`)
- **Фильтры:** `--name`, `--login`, `--group`, `--uuid` (точное совпадение; `--name` можно с `*`-glob).
- **Результат фильтрации:**
  - 0 записей: ошибка, код выхода 2;
  - больше 1: ошибка со списком `name / login / group / uuid` в stderr, код выхода 3;
  - ровно 1: продолжаем.
- **Поля:**
  - встроенные: `password` (по умолчанию), `login`, `name`, `uuid`, `totp`;
  - атрибуты: любое другое имя ищется в `stringFields` по ключу `KPH: <ИМЯ>`. Префикс `KPH: ` убирается, имя сравнивается с учётом регистра.
- `stringFields` приходит как массив объектов `{ "KPH: X": "v" }`. Его нужно нормализовать в `Map`.
- **Устаревшие записи:** с `expired` выводится предупреждение в stderr, но запись не блокируется.

## 5. Команды (`cli.ts`)
**`kpx get <url> [-f FIELD] [фильтры]`**
- Выводит значение поля в stdout без перевода строки, но добавляет его, если stdout — терминал.

**`kpx env <url> [фильтры] [--format env|shell|json] [--prefix P] [--only A,B]`**
- Выводит все `KPH:`-атрибуты записи. Опционально `--with-login=VAR` и `--with-password=VAR`.
- Форматы:
  - `env`: `KEY="..."` с экранированием `\`, `"`, `$` и переводов строк, в формате dotenv;
  - `shell`: `export KEY='...'` с экранированием `'` как `'\''`, для использования через `eval`;
  - `json`: объект.
- Имена атрибутов, которые не подходят как имя переменной (`^[A-Za-z_][A-Za-z0-9_]*$`), пропускаются с предупреждением.

**`kpx render <template> [-o out] [--mode 600]`**
- Синтаксис: `{{kp:<url>#<field>}}`. С фильтрами: `{{kp:<url>#<field>?name=X&login=Y}}`.
- Всё за пределами `{{kp:…}}` копируется без изменений. `\{{` экранирует фигурные скобки.
- Ответы кешируются по паре `url+фильтры`, поэтому для каждого URL достаточно одного запроса и одного окна подтверждения.
- Файл записывается атомарно: сначала tmp, потом rename, с правами 600 по умолчанию.
- Если хотя бы одна подстановка не удалась, ничего не записывается, и в stderr выводятся все ошибки.

**`kpx run <url> [фильтры] -- cmd args…`**
- Запускает команду с атрибутами в env (через `spawn` с `stdio: inherit`) и возвращает её код выхода.

**`kpx associate`, `kpx status`**
- `status` показывает: proxy найден, версия KeePassXC, база открыта, ассоциация действительна.

**Общие правила**
- Секреты выводятся только в stdout, диагностика — в stderr, флаг `--quiet`.
- Коды выхода:
  - 0: успех;
  - 1: общая ошибка;
  - 2: запись не найдена;
  - 3: неоднозначный выбор;
  - 4: база заблокирована (таймаут разблокировки);
  - 5: ассоциация отклонена.
- Секреты не пишутся ни в логи, ни в сообщения об ошибках.

## 6. Тесты (vitest)
- **Фрейминг:** фреймы, разбитые на части, и несколько фреймов в одном чанке.
- **Nonce:** инкремент, включая переполнение байта.
- **Fake KeePassXC:** in-memory транспорт, который реализует серверную сторону на tweetnacl. Через него проверяются обмен ключами, associate и test-associate, get-logins, коды ошибок, сценарий unlock и нежелательные сообщения.
- **Выбор и поля:** выбор по фильтрам, извлечение `KPH:` и встроенных полей.
- **Форматы env и shell:** экранирование кавычек, `$`, переводов строк и юникода.
- **Шаблоны:** разбор, экранирование, кеширование, отказ от записи при ошибке.
- **Интеграционный тест:** только вручную, по флагу `KPX_E2E=1`, против реального KeePassXC.

## 7. Документация (`README.md`)
- **Настройка KeePassXC:**
  - включить Browser Integration;
  - в разделе «Дополнительно» включить «Возвращать дополнительные строковые поля "KPH: "»;
  - включить «Возвращать только наиболее подходящие»;
  - по желанию отключить подтверждение доступа или ставить «Запомнить».
- **Соглашение для записей:** поле URL указывает на ресурс (`http://loto.dev/players`), переменные хранятся в атрибутах `KPH: NAME`.
- **Примеры:**
  - `kpx get http://loto.dev/players`;
  - `kpx env http://loto.dev/players > .env`;
  - `eval "$(kpx env … --format shell)"`;
  - `kpx render .env.tpl -o .env`;
  - `kpx run … -- pnpm dev`.
- **Как отозвать доступ:** настройки базы → Browser Integration → удалить ключ «wsl».

## 8. Проверка готовности
- `pnpm lint`, `pnpm test` и `pnpm build` проходят.
- Ручная проверка на реальном KeePassXC:
  1. первая ассоциация (появляется окно);
  2. повторный запуск без окна;
  3. работа с заблокированной базой (появляется окно разблокировки, потом запрос повторяется);
  4. `get`, `env` и `render` на тестовой записи с `KPH:`-атрибутами и URL с путём.

## Риски и что проверить первым
- **Запуск proxy из WSL.** Сначала нужно убедиться, что `keepassxc-proxy.exe` нормально работает без аргументов браузера: отправить один `change-public-keys` и получить ответ. Это стоит сделать маленьким прототипом до основной работы.
- **Буферизация stdout.** Иногда WSL interop буферизует вывод Windows-процессов. В этом случае фреймы нужно читать без ожидания конца строки (бинарный поток уже так и работает).
